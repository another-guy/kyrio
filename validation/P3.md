# P3 validation — port to a second machine

P3 is the only phase that tests I1 and I2 against reality rather than against a
lint. Everything before it is an argument that this pack is portable; this is
the measurement.

**It is not optional and not reorderable.** Porting with three skills surfaces
leaks cheaply. Porting with nine means rewriting nine.

---

## What P3 is

Take a machine that has never run this pack. Install from the marketplace, and
run every flow P1 and P2 shipped.

**The acceptance criterion is a single sentence:**

> Every P1 and P2 flow runs on the second machine with **no edit to any tracked
> file**, and at least one capability is served by a **different transport**
> than on the first machine.

The first half tests I2 — nothing in the repository assumes a particular
machine. The second half tests I1 — skills describe work, not providers, so a
skill cannot notice that what serves it changed.

If a tracked file had to change, that edit **is the finding**. Record it, fix
it in the repository, and re-run. Fixing it only on the second machine converts
a portability defect into two machines that disagree.

## What counts as a leak

| leak | how it shows up |
|---|---|
| **Path** | An absolute path, a home directory, a drive letter, or a separator that only exists on one platform |
| **Interpreter** | Assuming a particular Python name, version, or install location |
| **Shell** | A construct one shell has and another does not |
| **Encoding** | Output that renders on one console and not another; a mark that dies on a legacy codepage; a line ending that breaks a shebang |
| **Transport** | A skill that behaves differently, or worse, because a capability is served another way |
| **Provider** | Anything outside `providers/` that only makes sense for one product |
| **State** | Something written on the first machine that the second turns out to need |
| **Configuration** | A key the first machine set that the second cannot discover on its own |

The last three are the expensive ones. The first five are usually a one-line
fix; those three mean something is in the wrong layer.

## 0. Choose the machine

It must be **cold** — the plugin never installed, no `~/.claude/kyrio/`.

```sh
ls ~/.claude/kyrio
```

**Expect** it to be absent. If it exists, this machine cannot validate the cold
path. Either use a different one, or move the directory aside and say so in the
result table, because a machine that has been set up before does not prove that
setup works from nothing.

Prefer a machine that differs from the first in more than one way — a different
operating system, a different shell, a different Python install, a different
console encoding. Two machines that are nearly identical validate nearly
nothing.

## 1. Cold install

```
/plugin marketplace add <this repository>
/plugin install kyrio
```

Restart, then:

```sh
kyrio help
```

**Expect** a framed response. Nothing has been configured, and that must not
matter yet.

**Note anything you had to do by hand to get this far** — a permission granted,
a file made executable, a shell restarted, a security prompt answered. Each of
those is either documentation that is missing or a leak. Neither is nothing.

## 2. Zero-configuration first

P1 shipped two skills that resolve no transport and need no setup. They are the
cleanest possible test of I2, because on a cold machine there is no
configuration to hide behind.

```
/kyrio:orient
/kyrio:trace <symbol>
```

**Expect** both to work **before setup has ever run**, inside any git
repository on this machine.

**Fails if** either asks for configuration, names a provider, or produces
something that reads as though it were written on the other machine.

Also run the local capability directly:

```sh
kyrio repo map
kyrio repo churn --since 90d
kyrio repo owners
```

**Expect** `local` transport, no network, no credential, answers on any
repository.

## 3. Setup from nothing

```
/kyrio:setup
```

This is the first time Pass 2 is being exercised as designed — on the first
machine there was already evidence to propose from.

**Expect:**

- Pass 1 proposes **only** what evidence supports: a connected server, or a
  tool that answered `authenticated`. On a cold machine this may be nothing at
  all, which is a correct outcome and not a failure.
- Pass 2 asks about everything left, and *not used here* stays distinct from
  *not sure yet*.
- The result is written to this machine's own layer, and **nothing was copied
  from the first machine**.

```sh
kyrio caps
kyrio config explain
```

**Expect** each value attributed to a layer, and no value that could only have
come from somewhere else.

## 4. Deliberately serve something differently

This is the step that has no equivalent on one machine, and the reason P3
exists.

Configure a capability on this machine with a **different transport** than the
first machine uses. The cheapest version: set `scm` to `manual` here.

```sh
kyrio probe record --set scm=manual
kyrio scm pr diff <id>
```

**Expect** `{"status":"manual",...}` with instructions that end at
`kyrio ingest text --file <path>`, and that **name no product**.

Then follow them, and continue:

```sh
kyrio ingest text --file <path>
```

**Expect** the flow to carry on. The skill must not notice the difference.

Then run the whole review flow against the manual transport:

```
/kyrio:review <id>
```

**The check that matters:** the skill's behaviour, questions, and output shape
are the same as on the first machine. Only the transport differs. A skill that
reads better with one transport than another has provider knowledge in it that
the lint could not see (I1).

## 5. Everything P2 shipped

Run `validation/P2.md` on this machine, start to finish, and fill in its result
table. Do not summarize it here — a checklist copied is a checklist that
drifts.

Two steps deserve attention specifically because the machine is different:

- **Step 3's console check.** A different machine is the natural place to test
  a non-UTF-8 terminal. Server statuses classify on words, never on the marks
  beside them.
- **Step 5's diff counts.** They are parsed, not reported. A different tool
  version can change what comes back.

## 6. Cross-machine checks

These can only be made now that two machines exist.

**Nothing tracked changed.**

```sh
git status --short
git diff --stat
```

**Expect** empty. Any edit that was needed to make this machine work is the
finding, and belongs in the repository, not on this machine.

**The two machines disagree only where they should.** Compare
`kyrio config explain` on both. They may differ in transports, providers, and
paths. They must not differ in schema, in which capabilities exist, or in what
any command is called.

**No output names the other machine.** Read this machine's configuration and
recorded state. A capability entry records a transport and a provider; it must
not record a host, an account, or a path that would say where either machine
sits.

**The checks pass here too.**

```sh
python3 plugins/kyrio/scripts/check_portability.py
python3 -m unittest discover -s plugins/kyrio/tests -t plugins/kyrio/tests
```

**Expect** clean and green. A test that passes only where it was written is not
a test of anything portable.
