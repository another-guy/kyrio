# P2 validation

What P2 shipped: transport resolution, execution probing, connected-server
discovery, capability entries written to the machine layer, setup's two passes,
the first `scm` adapter, `scm pr diff`, `scm log`, `scm pr comment`, and the
`review` / `review-pass` skills.

This is a **manual pass**. The test suite covers what can be checked without a
real machine, a real credential, and a real change under review; everything
below is what it cannot. Run it once per machine, and record the result at the
bottom — a check that has only ever run on the machine it was written on has
not been validated (I2).

**Conventions.** `<repo>` is a repository this machine can actually reach, and
`<id>` a change in it that already exists. Every response is a one-line JSON
header, `---`, then the payload; unless stated otherwise, read the header.
Commands are run inside Claude Code with the `!` prefix, because the plugin's
`bin/` is on the Bash tool's `PATH` only there.

---

## 0. Preconditions

| | |
|---|---|
| Python 3.12+ resolvable | `!python3 --version` |
| Plugin installed and current | `/plugin update`, then restart |
| A tool the `scm` capability can use | see step 3 |

An older Python is a legitimate outcome, not a skipped test: the launcher must
answer with a framed `error` naming the floor version, never a shell error.

## 1. The broker answers at all

```sh
kyrio help
kyrio caps
```

**Expect** `{"status":"ok",...}` on both, exit 0.

**If it fails** the shim did not find an interpreter. The payload says which
names it tried. This is the only failure that arrives before Python runs, so a
bare shell error here — rather than a framed response — is itself a defect.

## 2. Configuration reads the same from anywhere

```sh
kyrio config explain
kyrio --cwd <repo> config explain
```

**Expect** each value attributed to the layer behind it, and no absolute path
from another machine anywhere in the output.

**Regression, fixed in `bdb5abe`** — a `--cwd` that names nothing must be
refused as a caller mistake, not reported as a broken tool:

```sh
kyrio --cwd /no/such/place caps
```

**Expect** `{"status":"error","message":"--cwd is not a directory: ..."}`.

**Fails if** the response instead says a tool is not installed. That was the
original bug: a failed `chdir` and a missing binary are one `ENOENT` on POSIX,
and reporting both as *missing* accuses a working tool.

## 3. Probing: execution, not presence

```sh
kyrio probe
kyrio probe servers
```

**Expect** in `TOOLS`, for a machine with a signed-in SCM tool:

```text
TOOL      CAPABILITY  STATE
<tool>    scm         authenticated
```

**The three states are different results, and all three are valid:**

| state | means | what it proves |
|---|---|---|
| `authenticated` | ran, and someone is signed in | usable |
| `not authenticated` | ran, nobody signed in | installed, entitlement unknown |
| `not installed` | did not run at all | nothing to configure here |

**Check the distinction is real** by signing the tool out and re-running. A
build that reports `authenticated` for a signed-out tool is worse than one that
reports nothing, because setup will propose it.

`probe servers` classifies on the **words** of each status, never the mark
printed beside it. On a console using a legacy codepage the marks do not
survive, so run this at least once in a terminal that is not UTF-8 and confirm
the classification is unchanged. A status this version does not know must come
back as `unknown`, repeated verbatim, never rounded.

## 4. Setup asks in two passes

```
/kyrio:setup
```

**Pass 1 proposes only from evidence** — a connected server, or a tool that
answered `authenticated`. Nothing else may be proposed.

**Pass 2 asks about everything left**, and the four answers must stay distinct:

| answer | recorded as |
|---|---|
| names what serves it | that transport |
| served by hand | `manual` |
| not used here | `unavailable` |
| not sure yet | **nothing written** |

**The check that matters:** *not used here* and *not sure yet* must not collapse
into the same entry. The first is an answer and stops the question being asked
again; the second is the absence of one and must leave the capability
unconfigured.

**Then confirm setup wrote nothing by hand:**

```sh
kyrio caps
kyrio config explain
```

Every capability agreed in either pass appears, attributed to the machine
layer. Re-running setup and answering the same way must produce the same
configuration.

## 5. `scm pr diff`

```sh
cd <repo> && kyrio scm pr diff <id>
```

**Expect** a header carrying the counts, then the diff verbatim:

```text
{"status":"ok","kind":"diff","files":4,"added":61,"removed":12,...}
```

**Verify the counts against the change itself.** They are computed here by
parsing the unified diff, not reported by the tool — a unified diff is a
format, not any one provider's format. If the tool returns anything other than
a raw unified diff, the payload still looks right and the counts are silently
wrong. This is the single most likely failure in P2 and the only one that is
invisible without checking.

**Negative cases, each a different response:**

| input | expect |
|---|---|
| an id that does not exist | `error`, carrying the tool's own words |
| an id the adapter would not recognize (`main`) | `error`, and **nothing launched** |
| run from a directory that is not a repository | `error` naming that, not the tool |
| capability unconfigured | `unavailable`, with a remediation |
| capability set to `manual` | `manual`, ending at `kyrio ingest` |

The `manual` path is not optional to test. It is the fallback every machine
without an adapter depends on, and its instructions must name no product.

## 6. `scm log`

```sh
cd <repo> && kyrio scm log
cd <repo> && kyrio scm log --since 30d
```

**Expect** one row per merged change with `id`, `at`, `author`, `title`, oldest
or newest first but **consistently**, and the window honoured. An empty window
is `ok` with no rows, never an error.

## 7. `scm pr comment` — draft first

Draft, which must send nothing:

```sh
kyrio scm pr comment <id> --file <path> --line <n> -f <body-file>
```

**Expect** `{"status":"draft",...}`, exit 0, and **verify on the change itself
that nothing was posted.** A draft that posts is the most costly defect in this
phase: it puts words under the user's name on someone else's work, and deleting
the comment does not unsend the notification.

Then, on a change nobody is watching:

```sh
kyrio scm pr comment <id> --file <path> --line <n> -f <body-file> --post
```

**Expect** `{"status":"ok",...}` and the comment visible, anchored to the right
file and line. Two calls happen here — the head revision is resolved first,
then the comment posted against it. Confirm the anchor is correct rather than
merely present; a comment on the wrong line is worse than no comment.

**Also check** the body arrives with its formatting intact, including newlines
and any character the shell would otherwise interpret. The body travels as a
file for exactly this reason.

## 8. The review skills

```
/kyrio:review <id>
```

**Expect, in order:** the diff fetched, surrounding code read, `review-pass`
invoked, findings reconciled, findings shown, and **a question before anything
is posted**.

**The check that matters is that `review-pass` runs without this
conversation.** It declares `context: fork`. That the frontmatter validates
proves only that it was not rejected — it does not prove it forked. Confirm it
fetched the diff itself rather than receiving one. A pass that inherits the
context that produced the change is theatre, and it will still produce
plausible findings, so this cannot be checked by reading its output alone.

**Also confirm:**

- With `output_root` unset, the skill says so and stops **before** drafting.
- Nothing is written inside `<repo>`. `git status` there is unchanged (I7).
- A review that finds nothing says so. An invented finding is a failure.

## 9. Portability

The point of P2 is that none of the above is coupled to one machine.

```sh
python3 plugins/kyrio/scripts/check_portability.py
python3 -m unittest discover -s plugins/kyrio/tests -t plugins/kyrio/tests
```

**Expect** clean, and all tests passing, on every machine — not only the one
where they were written.

Then read the machine's own configuration and confirm it names nothing that
would identify where it runs. A capability entry records a transport and a
provider; it must not record a host, an account, or a path that would say
where this machine sits (I1, I2).
